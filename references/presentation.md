# 英文优先的双语 README 与图片

先读实际项目并运行适用验证，再写介绍。面向第一次看到仓库的人说明“解决什么问题、能看到什么、怎样开始”。不从包名推测功能，不用空泛夸赞填充。

## 语言与文件组织

默认 `README.md` 使用英文，`README_ZH.md` 提供完整中文版本，顶部均显示 `English | 中文` 并互相链接。已有 `README.zh-CN.md` 等中文文件则沿用，不制造重复译本；保留真实存在的其他语言入口。仍用中文与用户沟通。

不要在主 README 首屏交替堆叠中英两大段。用户明确要求单文件双语时，先完整英文，再完整中文，顶部使用页内语言导航。正常默认是两个文件。

两版简介、功能、安装步骤和截图对应同一项目版本；中文应自然表达同一价值，避免逐词硬译。语言导航只链接已交付的译本。

## 首屏：先说明价值，再引导行动

借鉴 CC Switch、uv、Ollama 的信息组织，依据项目规模选择密度。首屏默认顺序：

1. **项目名**：一级标题；有真实 logo 时可搭配，保持一眼可辨。
2. **英文定位句**：简短副标题，通常 6–16 个词，说明“什么工具 + 用于什么对象/场景”。
3. **加粗价值简介**：一到两句自然英文，说明用户能完成的关键动作、得到的结果和最有区分度的能力。先写使用价值，技术实现放到后文。
4. **真实入口**：有已核实的项目官网/演示站才展示；徽章只使用已有版本、许可证或 CI 的真实状态，控制数量。
5. **语言切换**：`English | [中文](README_ZH.md)`；中文版链接回英文主文件。
6. **快捷导航**：按实际内容选择 `Quick Start · Features · Documentation · FAQ` 等少量链接。只有已有可下载发布包才放 `Download`；只有有对应内容才放 FAQ、Changelog、User Manual。CLI/库优先 `Installation`、`Quick Start`、`Usage`。
7. **主图与短图注**：一张能体现真实价值的截图、效果图或封面，与上述文案一致。不要用空白占位、失效链接或长空行把介绍与图片隔开。

在 Markdown 中合理使用标题、加粗、短段落和分隔点；仅当图标和链接成组时使用 GitHub 支持的简单居中 HTML，并保留正确空行。确保窄屏能自然换行，不依赖自定义 CSS。

“All-in-One”仅用于实际整合多个重要功能的项目；“fastest / only / best”、性能倍数、用户量和兼容平台必须有事实依据。不要照搬参考项目的官网、赞助商、官方唯一性声明或品牌标识。

### 写法示例

以下以本 Skill 为例，展示定位与价值文案；其他项目必须依据自身功能重写：

```markdown
# GitHub Publish

### A project publishing workflow for GitHub

**Prepare project files, check sensitive content, and publish with your GitHub identity — complete with bilingual documentation and project visuals.**

English | [中文](README_ZH.md)

[Quick Start](#quick-start) · [Features](#features) · [Usage](#usage)
```

这段示例之后放实际生成并查看过的项目主图，再提供上述链接对应的正文。示例中的文件和锚点必须随输出一并落实，不能原样复制后留下断链。不要把本示例当作已生成的项目 README。

## 正文：让读者尽快用起来

首屏之后先用少量真实亮点或简短 `Why <Project>?` 说明用途，再进入安装和最小成功示例。默认组织为：

- **Features / Highlights**：三到五个已实现能力，复杂功能用表格或短演示。
- **Quick Start / Installation**：必要依赖、安装、运行与最小结果；命令必须验证，不让用户先阅读长架构介绍。
- **Usage / Configuration**：典型操作、占位符配置和示例文件链接。
- **Documentation / FAQ**：仅在有实际内容时加入，长细节放文档链接。
- **Contributing / License**：保留用户公开署名、真实来源和已有许可证；没有许可证不擅自添加 MIT。

可根据项目调整顺序，短项目合并章节，不机械堆齐所有标题。技术栈、项目结构与架构只在有助于使用或贡献时加入。仓库 About 采用简短的 `English value proposition. | 中文简介`，与首屏定位一致。

标题层级清晰、段落短、配色一致。README 主图采用已选定素材目录下的相对路径（如 `assets/` 或 `docs/images/`）和对应语言替代文字，沿用现有合理位置，不依赖本机路径。不要上传写 README 的提示词、对话或规划。

若展示目录树，按整理后的真实结构生成，只列有助于使用或贡献的入口，不为示例结构创建空目录。Release 的下载链接仅在对应版本和附件真实存在、已核验后展示；源码归档与安装包在文案中明确区分。

## Release 版本说明

默认同一份说明先英文、后中文，信息一致。依据实际提交差异和验证结果写本版本的亮点、修复、适用平台、安装方式及确实存在的兼容性变化；没有变化的类别省略。首次版本说明项目已有能力，后续版本说明相对上一版本的变化，不复制整个 README 或未经核对的提交日志。

有下载附件时列清版本、系统、架构、包类型及校验方法；只承诺实际构建并检查过的平台。没有签名或测试证据时不写“已签名”“全平台测试通过”。发布步骤、附件校验和链接核验见 [Release 流程](releases.md)。

## 按项目选择图片

### 有界面

运行真实项目，以合成/演示数据进入最能说明价值的界面，截图前关闭私人通知、账号菜单和含个人路径的调试窗口。优先一张干净主图，复杂功能再加少量截图。需要动画时才制作短 GIF，避免无意义大文件。

截图必须来自当前版本。不能把 AI 生成的界面或设计稿标为“运行截图”。隐私问题优先通过清空演示数据重新截图解决。

### CLI、库、Skill、后台工具

优先展示真实最小调用及结果，或创建准确的输入→处理→输出说明图。可补充与项目实际功能匹配的设计封面；无 UI 并不意味着必须伪造 UI。

有 imagegen 能力且需要栅格封面时使用它：先从真实功能提取视觉主题，采用简洁构图，尽量少嵌入长文字。图注注明“项目封面/概念示意”；生成素材不代表功能已运行。没有 imagegen 时使用可验证的流程图、项目已有素材或真实输出截图，至少交付一种合适的项目图片。

生成或编辑图片时遵循当前环境可用的图片工具要求；不把私人源码、密钥、客户数据或含隐私截图作为生成请求素材。图片只使用项目公开定位和演示内容。

## 发布前视觉检查

- 实际打开每张新增或修改的图片，检查文字拼写、清晰度、内容真实性、裁切和画面隐私。
- 检查 EXIF/XMP/文本块、作者、GPS 等元数据；SVG 还检查源码、外链、脚本及嵌入资源。清理的是副本，不覆盖用户原始素材。
- 在可信的本地 Markdown 渲染器/预览中查看 README；如缺预览工具，先补齐可用预览方式，不声称完成视觉 QA。
- 检查英文首页、中文译本在桌面和约 390px 宽度的阅读效果；验证语言切换、快捷导航、正文锚点、中英对应关系及所有图片/运行说明链接。
- 更新生成内容后重新做文件、暂存区和提交检查。图片的人工复核记录须绑定最终字节哈希；重新导出后旧记录失效。

对于已经存在且经过检查的优质 README 与图片，保留有价值的内容和素材，在落实英文首页与中文切换的前提下做必要调整，不无故重写整份文档。

- [uv](https://github.com/astral-sh/uv)：简短定位、证据图片、功能亮点与安装说明。
