# 上传前的轻量源码整理

目标是让陌生人能找到入口、安装运行、阅读文档和参与贡献，同时保持项目行为。每次上传都评估结构；已经清楚的项目无需为了显得专业而搬文件。

## 整理顺序

1. **识别约定**：读取依赖清单、锁文件、运行与构建配置、测试、打包清单、CI 和相对路径引用。先确认项目类型、真实入口与能运行的命令，再决定放置位置。
2. **划分内容**：依据 [文件规则](content-policy.md) 排除过程材料和隐私，分别列出源码成品、Release 附件候选及待核实项。未知文件先查看，不随手删除。
3. **选择最小调整**：保留已成型的结构；可安全移动的零散使用文档、展示图片、辅助脚本分别归拢到现有对应目录。只在有实际内容时新建目录。单脚本留在根目录完全合理。
4. **落实到正确副本**：首次发布仅整理独立发布目录，原目录和历史不动；已有仓库在受控工作区中修改并正常提交，保留本地过程文件副本及其他未提交工作。
5. **同步引用并验证**：移动后更新 import、入口声明、资源路径、打包配置、CI 命令及文档链接。检查 Windows/Linux 路径大小写和带空格路径。运行受影响的现有测试、最小启动或构建，核对实际分发包内容；无法确认安全的路径迁移暂缓，保留可用布局。
6. **复核差异**：展示简短整理摘要和最终清单，不生成要上传的整理计划/操作日志。确认未改变业务、依赖版本、许可证、历史和真实署名，再进行 files、staged、commits 检查。

## 常见位置：按需要选用

下表是生态惯例的组合，不是要求每个仓库建齐所有目录，也不是 GitHub 的强制目录标准。

| 内容 | 放置建议 |
|---|---|
| 项目入口说明 | 根目录英文 `README.md`、中文译本（默认 `README_ZH.md`），导航互链 |
| 依赖与构建 | 保留生态要求位置的清单、锁文件、构建配置，不能为清爽移动必需根文件 |
| 源码 | 沿用根脚本、`src/`、`app/`、包名目录、`crates/` 等既有布局 |
| 测试 | 沿用框架约定的 `tests/` 或与源码相邻的测试位置 |
| 使用文档 | 较长指南归入现有 `docs/`，简短说明可留 README；不放 AI 对话或实现计划 |
| 图片与运行资源 | 沿用 `assets/`、`docs/images/`、`public/` 等合适目录；区分展示图片与运行时必需资源 |
| 辅助脚本与示例 | 有需要才用 `scripts/`、`examples/`；示例配置全部使用占位符 |
| GitHub 协作配置 | 有真实用途才保留或补充 `.github/`；不为排面生成未经测试的 CI、虚构安全邮箱或空模板 |
| 许可证与贡献 | 保留已有 LICENSE、NOTICE 和贡献说明；不自动选择许可证或删除第三方归属 |
| 安装包与分发压缩包 | 构建到单独输出目录，明确列为 Release 附件；通常不进源码 Git 历史 |

`.gitignore` 根据项目技术栈补齐缓存、虚拟环境、本机配置及可重建输出，不能盲目忽略所有 `build/`、`dist/` 或全部二进制；有些项目运行确实需要这些内容。已有跟踪文件和历史仍按发布规则审查。

## 项目类型示例

- **单文件 Python 工具**：`app.py` 留根目录；`pyproject.toml` 若引用 `app:main`，不为新建 `src/` 破坏导入。保留测试，较长指南和截图可安全归类，更新 README 链接后跑实际命令。
- **Web / Tauri 桌面项目**：保留框架的 `src/`、`app/`、`public/`、`src-tauri/` 和配置位置。CC Switch 的前端、桌面端、测试和文档分开可供参考，不照抄其全部目录。
- **Python 包 / Rust 工作区**：沿用当前 flat 或 src 布局、包发现设置、`crates/` 成员及 workspace 清单。发布整理不触发整包迁移。
- **Skill / 插件**：保持发现机制要求的 `SKILL.md`、`agents/`、`scripts/`、`references/`、必要插件清单及资源位置，不能把整个产品塞进新建 `src/` 导致无法发现。
- **已有清晰结构的项目**：核实清单、更新必要说明和忽略规则即可。已有外部用户依赖的路径/API 更应保持稳定。

不在发布整理中自动升级依赖、批量格式化、改业务逻辑、改公共 API、引入新构建系统或拆分仓库。需要这些工作才能正常运行时，报告具体阻碍并单独解决，不能把破坏性改造伪装为轻量整理。

## 参考依据

- [GitHub 仓库最佳实践](https://docs.github.com/en/repositories/creating-and-managing-repositories/best-practices-for-repositories)：完善 README、必要的协作说明和仓库安全；该文档没有规定统一源码目录。
- [CC Switch](https://github.com/farion1231/cc-switch)：按桌面应用技术栈组织前端、Tauri 后端、测试、文档及资源。
- [uv](https://github.com/astral-sh/uv)：按 Rust 工作区及 Python 集成组织源码，说明成熟项目也会因生态选择不同布局。

参考其可导航、可构建、说明齐全的方式，不以星数作为某个目录结构适合当前项目的证据。
