# GitHub Release：版本源码与下载附件

仅在用户明确要求 Release、发布版本或分发下载包时使用。普通“上传源码/更新仓库”按 [源码发布流程](publishing.md) 完成，不自动发版。已授权发布版本且目标明确时，完成下面步骤后直接发布；草稿是组装步骤，不是额外审批关卡。仅要求准备草稿时才停在草稿。

## 三类内容

| 内容 | 来源与用途 |
|---|---|
| Git 仓库源码 | 保留项目所需源文件、依赖、文档与资源，正常提交并推送 |
| Release 自带 Source code (zip/tar.gz) | GitHub 根据版本标签对应的源码快照自动提供，无需另传原工作区压缩包 |
| Release assets | 单独上传的安装包、可执行文件、wheel、插件分发包等，来自同一已检查提交，附双语版本说明和校验文件 |

源码归档不是编译好的程序。自动归档不携带完整 `.git`，但不能因此忽略仓库可达历史中的秘密。LFS 是否含真实对象受仓库设置影响，子模块也不能假定被完整打包；涉及它们时核实真实下载内容。

## 1. 固定版本和源码

1. 确定仓库、版本号、目标完整 SHA、稳定版/预发布及附件平台。沿用项目版本约定，保持版本清单与标签一致；版本无法从明确目标或现有发布配置确定时只询问这一缺项，不自行假设 `v1.0.0`。
2. 读取已有 tags、Releases 和 `.github/workflows/`，确认是否已有自动发版流水线、是否启用不可变 Release。先确认 tag push / release publish 将触发什么操作，再推送；不能和 CI 同时抢发同一个版本。
3. 完成必要版本文件更新和源码三层检查，以已核实的用户身份提交，按源码流程推送并核对**确定 SHA**。不要在检查完后临时修改版本号却沿用旧 SHA 或旧报告。若源码已在远程，仍审查该快照及本次新增可达历史；不能只因“已经上传”免查。
4. 已有 tag 时解析到实际 commit（附注标签需解引用），必须等于本次目标 SHA。不自动移动、删除或覆盖现有标签。任何历史污染或身份问题仍按主流程阻止上传。

## 2. 从确定提交构建并审查附件

从目标 SHA 的干净检出/导出副本执行项目已有、可核实的构建或打包命令，使用锁定依赖和需要的工具链。记录构建命令、平台及产物与 SHA 的对应关系，记录留在本地工作资料中。构建输出与源码发布清单分开；不要压缩原工作区，也不要仅凭旧 `dist/` 文件名宣称来自本版本。

没有可编译产物的库、纯源码项目或 Skill，可以只提供 GitHub 自带源码归档和版本说明；若用户明确要可安装 Skill/插件包，按安装器需要的根目录结构导出必需文件，检查解压后的发现路径，不虚构 exe 或多平台构建。典型附件命名为 `<project>-<version>-<os>-<arch>.<ext>`，平台无关包使用对应生态惯例。

所有要上传的最终文件，包括压缩包、签名文件、更新清单、文件名和版本说明，必须单独审查：

- 用 `preflight.py files` 对附件目录的明确清单运行检查，按 [检查用法](preflight.md) 处理。归档递归检查内部内容，图片检查画面和元数据；二进制还须确认内嵌资源、配置、调试路径及打包附带数据，确认无秘密或个人数据。
- 扫描器不认识的格式、加密包、未检查的二进制和超限项都不能默认为安全。当前脚本的单文件 20 MiB、总量 256 MiB 等限制见检查用法；不能修改状态、伪造人工复核或只扫文件名来绕过 `incomplete`。固定大小/格式能力限制按 [附件替代审计](preflight.md#release-附件超出脚本能力时) 实际补齐完整证据，并保留原报告；缺工具、工具失败或审查不完整仍停止上传。源码扫描通过不等于附件通过。
- 签名私钥和密码始终留在受保护环境中；签名/公证/压缩全部结束后，再绑定最终字节哈希。重新构建、签名或打包使原检查记录失效。
- 为明确的下载附件生成 UTF-8 无 BOM 或 ASCII 的 `SHA256SUMS`，使用 SHA-256 与附件 basename，一行一个，不含本机绝对路径，不把校验文件自身算进去。重新检查校验文件与附件一致。普通校验和用于内容完整性，不能宣称等同作者数字签名。

不上传与本版本无关的旧产物，不用 `dist/*` 猜测附件。即使上传的是私有 Release，规则也相同。

## 3. 准备双语说明和标签

按 [版本说明规范](presentation.md#release-版本说明) 写 UTF-8 说明文件：英文在前、中文在后，真实变更、安装方法和平台对应一致。说明与短标签注释都检查隐私，不直接复用含私人路径/对话的构建日志或提交消息。说明和审计资料放在源码清单之外；需要维护的公开 CHANGELOG 可正常入库。

远程 tag 不存在时，使用已核实的用户本地身份创建指向已检查 SHA 的附注标签，检查实际 tagger 与注释。将标签元数据导出为临时文本，做秘密扫描与隐私复核；提交审计不会自动扫描 Git tag 对象。显式推送这一个标签，再读取远程解引用后的 SHA 核对。以下是替换占位符后逐步执行的命令示意，不可不经检查整段运行：

```text
git tag -a <tag> <checked-sha> -F <checked-tag-message-file>
git -c push.followTags=false push origin refs/tags/<tag>:refs/tags/<tag>
```

推送前重新核实标签对象、源码 SHA、附件哈希和远程状态未变。不用 `--tags`、`--force`，不让 Release 创建命令在默认分支最新位置自动造标签。

## 4. 先组装草稿，再发布

没有既有发版自动化时，先查目标 Release 是否存在。全部上传内容检查完成后，以已经存在于远程的准确 tag 创建草稿：

```text
gh release create <tag> --repo <owner/repo> --verify-tag --draft --title <title> --notes-file <checked-notes-file>
gh release upload <tag> <checked-asset-1> <checked-asset-2> <SHA256SUMS-path> --repo <owner/repo>
```

附件参数必须逐项来自清单，带空格/中文路径正确作为独立参数传入，不拼 shell 命令；没有附件时跳过 upload 和校验文件。预发布在 create 时加 `--prerelease`，并使用 `--latest=false`；旧版本补发也不要抢占 Latest。正常新稳定版按真实版本顺序核实 Latest 选择，不盲目覆盖现有更新版本。

读取草稿的 tag、标题、双语说明、附件名称/大小/哈希，与本地已检查记录一致后发布：

```text
gh release edit <tag> --repo <owner/repo> --verify-tag --draft=false
```

发布前复核状态。不可变 Release 在发布后锁定关联标签及附件，必须在草稿阶段备齐并验证。上传失败保留草稿，确认远程实际状态后仅补传缺失且已检查的附件；不能宣布发布完成。

**已有 CI 发版时**：沿用经核实的流水线，从指定 SHA 构建；检查下载到本地的确切 CI 产物后，按现有草稿/审批机制完成发布，不另开并行上传。若推标签即自动公开未检查产物，先解决流水线中的构建、扫描与发布顺序，不能先触发公开再补审计；不擅自部署一套新 CI 来替代现有流程。

## 5. 重试与同名冲突

- 已有 Release/tag 先读取再操作。tag SHA、目标状态、说明及附件哈希都匹配时可复用/跳过重复步骤，不重建同版本。
- 远程同名附件必须比较实际 SHA-256；有可靠 API digest 则核对，否则下载到独立临时目录计算，不能仅凭文件名和大小判相同。内容未知时先核实。
- 同名内容不同、标签指向不同提交时停止覆盖，说明差异并协调新版本或用户明确授权的处理方案。不默认使用 `gh release upload --clobber`，它会先删除旧附件；不可变 Release 不能这样替换。
- 不移动已发布标签，不通过改可见性使私有下载公开，不创建无关 Discussion、部署或包注册表发布。

## 6. 上传后验收

读取远程 Release，核对最终 tag 解引用 SHA、发布/预发布状态、Latest 选择、双语说明和仓库可见性。逐一核对附件名称、大小及 SHA-256；API 无 digest 时实际下载复算，并校验远程 `SHA256SUMS` 内容。查看版本页下载入口，抽查自动源码归档的必要文件、路径及特殊资源完整性。

说明链接及 README 的 Download 入口只指向实际存在、适用于当前读者权限的版本/附件。需要更新 README 链接时走正常源码提交与三层检查，不挪动已发布标签去包含后补文档。

最终报告仓库与 Release 链接、tag、源码 SHA、实际附件/校验文件及检查结果；缺少平台构建、扫描或发布失败时如实指出，不能将草稿说成已正式发布。
